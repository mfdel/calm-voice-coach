# ParentPilot v1 System Design

## Overview

`ParentPilot` v1 is a **manual SOS parenting coach** for iPhone. The parent taps into SOS mode, selects a common problem, optionally adds a short typed or voice note, and receives grounded advice generated by a hosted LLM using:
- child profile data
- parenting preferences and red lines
- relevant prior incidents
- retrieved guidance from a curated parenting knowledge base

This version is intentionally narrow:
- no passive listening
- no on-device reasoning / local LLM
- no village sync
- no predictive coaching

## Design goals

- Deliver first useful response in **< 5 seconds** on a normal connection
- Keep the UX one-handed and stress-friendly
- Minimize cloud exposure of sensitive family context
- Be better than a generic chatbot by grounding answers in structured data and curated parenting guidance
- Keep the backend simple enough for an MVP team to build and operate

## Core architecture choices

### Client
- Native iPhone app with `SwiftUI`
- Lock-screen / home shortcut into SOS flow
- Local encrypted storage for profile, preferences, red lines, and recent incidents
- Device-only speech transcription for short voice notes when available
- If device transcription is unavailable, unsupported, or fails, warn the user and offer text input instead

### Backend
- **Modular monolith** for v1, not microservices
- One main SOS orchestration endpoint: `POST /v1/sos/respond`
- Internal modules:
  - auth + request validation
  - retrieval engine
  - prompt builder
  - LLM adapter
  - response validator
  - incident logger

### Data + retrieval
- Curated knowledge base for ~25-30 common parenting problems
- `PostgreSQL` for operational data
- `pgvector` for semantic retrieval over knowledge snippets
- Hybrid retrieval:
  - exact problem filter first
  - age group + trigger filtering second
  - vector / keyword ranking third
  - incident-history boosting last

## Main request flow

### 1. SOS begins on device
- Parent taps widget or in-app SOS button
- App opens `SOSComposerView`
- Parent selects one of the common problem categories
- Parent optionally adds:
  - short typed note
  - short voice note

### 2. Input is normalized client-side
- Trim note length
- Remove obvious PII from free text where feasible
- If voice note is used:
  - attempt device transcription only
  - if unavailable, unsupported, or failed, show a warning and offer text input instead
- Build a compact request payload

### 3. App sends a single SOS request
Suggested payload:

```json
{
  "request_id": "uuid",
  "problem_category": "bedtime_resistance",
  "note_text": "She skipped nap and is screaming about pajamas.",
  "input_mode": "voice_plus_text",
  "child_snapshot": {
    "age_group": "toddler",
    "known_triggers": ["transitions", "fatigue"],
    "calming_preferences": ["choices", "quiet_voice"]
  },
  "parenting_snapshot": {
    "style": "gentle",
    "values": ["connection", "clear_boundaries"],
    "red_lines": ["cry_it_out", "physical_punishment", "shame_language"]
  },
  "recent_incident_ids": ["inc_101", "inc_089", "inc_071"]
}
```

### 4. Backend retrieval runs
The backend:
- validates problem category
- loads the relevant knowledge-base cluster
- pulls top matching snippets for:
  - same problem category
  - same age group
  - matching triggers / context terms
- loads a small number of recent incidents and feedback summaries

### 5. Prompt builder assembles context
Prompt sections are assembled in a strict order:
1. system instructions
2. family constraints and red lines
3. child profile snapshot
4. current situation
5. retrieved knowledge snippets
6. prior incident learnings
7. output schema contract

### 6. LLM generates structured response
- Non-streaming JSON response for v1 simplicity and easier validation
- Fast model tier preferred
- One retry only if output is invalid or violates red lines

### 7. Response validator runs before display
Checks:
- valid JSON
- required fields present
- script text included
- no obvious red-line violations
- suggestion count within expected bounds
- response length suitable for mobile display

### 8. Client displays response
The app renders:
- one short summary
- 2-3 recommended actions
- one exact script to say
- optional safety note

### 9. Incident is logged
Stored for later use in:
- retrieval boosting
- nightly debrief
- future ranking improvements

## Internal backend modules

### API layer
Responsibilities:
- auth
- request validation
- rate limiting
- locale handling

### Retrieval engine
Responsibilities:
- load KB candidates by problem category
- run hybrid ranking
- fetch relevant prior incidents
- return top snippets + scores

### Prompt builder
Responsibilities:
- assemble context in token-efficient order
- summarize prior incidents
- embed red lines as hard constraints
- produce a provider-neutral prompt contract

### LLM adapter
Responsibilities:
- provider abstraction for multiple LLM APIs
- translate the internal prompt contract into the selected provider's request format
- retries, timeouts, logging
- future-proofing for model swaps

### Response validator
Responsibilities:
- parse JSON
- enforce schema
- detect red-line conflicts
- downgrade or fallback if output is invalid

### Incident logger
Responsibilities:
- save normalized request + response metadata
- store feedback link for nightly debrief
- track latency and fallback metrics

## Voice transcription path

### Primary path
- Use iPhone speech transcription first for speed and reduced cloud exposure
- Only transcript text is sent in the SOS payload
- Raw audio is not persisted after transcription completes

### Failure path
- If local transcription is unavailable, unsupported for the user's locale, permission is denied, or transcription fails:
  - do not upload audio anywhere
  - warn the user that voice input is unavailable on this device or in the current configuration
  - offer text-only note entry as the fallback path
  - allow the parent to continue without a note if needed

## Safety and red-lines enforcement

Parent-defined red lines are enforced in 3 places:

### 1. Retrieval filtering
- Remove any KB snippets tagged as incompatible with a selected red line

### 2. Prompt constraints
- Tell the model not to recommend forbidden approaches
- Explicitly instruct it to prefer alternatives consistent with the parent's style

### 3. Post-generation validation
- Reject or retry if output contains:
  - forbidden tactics
  - shame-based phrasing
  - unsupported extreme advice

Fallback if validation fails:
- retry once with stronger constraints
- if still invalid, return a safe generic de-escalation response plus one curated script from the KB

## Latency budget

| Stage | Target |
|---|---:|
| UI open + problem selection state | 200 ms |
| Voice transcription (if used) | 700-1800 ms |
| Network round trip | 150-300 ms |
| Retrieval + ranking | 150-300 ms |
| Prompt assembly | 50-100 ms |
| LLM generation | 1500-2500 ms |
| Validation + formatting | 50-100 ms |
| Total | 2.8-5.0 s |

## Suggested API surface

### `POST /v1/sos/respond`
Single synchronous endpoint for MVP.

Returns:

```json
{
  "incident_id": "uuid",
  "summary": "She's overtired and struggling with the transition.",
  "suggestions": [
    {
      "title": "Offer one calm choice",
      "reason": "Choice reduces power struggle.",
      "script": "Do you want the star pajamas or the striped pajamas?"
    }
  ],
  "safety_note": null,
  "used_fallback": false,
  "latency_ms": 2430
}
```

### `POST /v1/incidents/{id}/feedback`
Nightly debrief feedback endpoint.

### `GET /v1/knowledge/metadata`
Optional client cache refresh for problem categories and KB metadata.

## v1 boundaries

### Included
- manual SOS flow
- typed notes
- short voice notes
- knowledge-base + RAG
- hosted LLM generation
- red-line enforcement
- nightly debrief feedback
- local encrypted cache

### Explicitly deferred
- passive listening
- on-device reasoning / local LLM
- smartwatch / whisper mode
- village sync
- predictive escalation detection
- rich analytics dashboards

## Recommended first implementation slice

1. static problem taxonomy
2. local child profile + preferences storage
3. one backend endpoint: `/v1/sos/respond`
4. one response schema
5. 5-7 seed problem categories before expanding to 25-30

This keeps the system buildable while preserving the long-term product direction.
